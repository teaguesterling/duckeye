# duckeye for Android: design

**Status:** approved by Teague, 2026-11-11. Phase 1 gate passed on the phone, 2026-11-11.
The app lives in `teaguesterling/duckeye-android` (private, created 2026-11-11). Nothing of the
real app is built yet, except the throwaway spikes this document cites.

## Intent

Teague: "instead of sharing a website to my printer, I want to share it to duckeye". A page,
or a file, shared from any Android app opens in a duckeye view on the phone. The view reads
like duckeye in a terminal, without the terminal.

## Goals

1. Share a URL or a file from any app to duckeye. It opens in a view.
2. Works away from home Wi-Fi. No homelab server or proxy (Teague's must-have).
3. The view is a real view, not a text dump: headings, lists, code, links, tables.
4. One copy of the conversion logic. The app runs the same SQL as the terminal duckeye.
5. v1 formats: HTML, markdown and plain text, panduck's formats (docx, epub, odt, org, tex
   and the rest), and source code. PDF comes in a later phase.

## Non-goals

- The CLI flags (`-S`, `-Q`, `-T`) as UI in v1. The view shows the whole document. A later
  phase can add an outline and section search.
- ZIM archives, duck_tails (git history), data profiling (`-Z`).
- iOS, desktop builds of the Tauri app.
- Logged-in pages. Every option re-fetches without the browser's cookies.

## Anti-goals (a failure even if it works)

- duckeye reimplemented in Kotlin, Java, Rust or JavaScript. The app calls SQL; it does not
  rewrite the conversion.
- A fork of the duckeye script, or any change to the terminal duckeye's output. Its output
  stays byte-identical.
- An app that loads unsigned extensions from a path anyone can write.

## Design

### The shape

```
share sheet ──intent──▶ MainActivity (generated by Tauri; ~20 lines of Kotlin for SEND)
                              │ URL or content:// URI
                              ▼
                        Rust command: fetch or read bytes ──▶ temp file in app cache
                              │
                              ▼
                        libduckdb.so (one file; extensions linked in statically)
                          SQL from `duckeye --emit-sql` + panduck's functions
                              │ blocks → HTML
                              ▼
                        WebView: renders the HTML; outline later
```

### The engine: one libduckdb.so, extensions linked in (Teague, 2026-11-10)

One DuckDB build makes the app's `libduckdb.so`. `STATICALLY_LINK_EXTENSIONS` (Makefile:158,
default `core_functions`) lists the v1 extensions, so they are linked inside it. This is
DuckDB's normal mechanism. So:

- one copy of the core, not one per extension. **Inferred:** the APK shrinks by well over
  half compared with loadable files. Not measured.
- no `LOAD`, no signature check, no trust patch. A statically linked extension is part of
  the binary.
- adding a format needs an app update. That is accepted.

**Per-extension isolation stays, as a check before the link (Teague's rule).** Each extension
first builds alone, with its own CMake build and its own `vcpkg.json`. Only an extension
whose solo build passes joins the linked build. A failure then names one extension, and the
others still ship.

**Corrected 2026-11-10.** The first draft said `PREBUILT_BINARY` with `PREBUILT_EXTENSIONS`
would link separately built extensions into one `libduckdb.so`. That is wrong. With
`PREBUILT_BINARY`, `CMakeLists.txt` imports `libduckdb_static.a` and never builds the
`duckdb SHARED` target (`src/CMakeLists.txt:96-100`). Upstream uses the option only to build
loadable extensions against a prebuilt core (`.github/workflows/OSX.yml:239`). A fresh
reviewer found this by reading the source, before any build.

v1 links: duck_block_utils, webbed (HTML), markdown, panduck v0.8.0 (docx, epub, odt, org,
tex and the rest), sitting_duck (code). **Corrected:** an earlier draft said the core already
links json, parquet and icu. It links only `core_functions` by default (`Makefile:158`). The
others build as loadable files, and the app does not ship them unless a phase adds them.

### Dependencies: vcpkg, one baseline

Spack has no Android platform. vcpkg's `arm64-android` triplet built all 18 stage 2 packages.
One binary can hold one copy of each library, so the linked build uses one vcpkg baseline:
DuckDB's `cd61e1e2`. The solo builds use the same baseline, so a solo pass predicts a linked
pass. A library that two extensions need resolves once. **Corrected 2026-11-11:** this said
libxml2 serves webbed and panduck. panduck v0.8.0's `vcpkg.json` lists pugixml, miniz and
yyjson; only webbed uses libxml2. miniz is shared, with zipfs, if zipfs is ever linked.

### The logic: the same SQL as the terminal

The app calls the macros that `duckeye --emit-sql` prints (the SQL-core design), plus
panduck's functions. The app's build runs `--emit-sql` and embeds the result, so there is one
copy. `--emit-sql` is a later phase of the SQL-core design. Until it exists, the app may
call only panduck and duck_block_utils functions directly. That is a gap to close, not a
second copy.

**Which reader, for which input. My call, temporary.** In the terminal, that choice is duckeye
logic (`case "$key"`). The SQL-core design moves it into a `duckeye_formats` table. Until that
table exists, the app carries a five-entry table from suffix or MIME type to reader, marked as
temporary in the code. Phase 5 removes it. That is a known second copy, kept small and named.

Reader per input: HTML → `read_html_blocks`. Markdown → `read_markdown_blocks`. panduck
formats → panduck's readers. Code → `ast_to_blocks` over `read_ast`. Rendering:
`duck_blocks_to_html`, so the view gets the same HTML that `duckeye -t html` writes.

### Share-in

Tauri has no share-target API. MainActivity in `gen/android` gets an intent filter for
`ACTION_SEND` (`text/plain`, which carries the URL, and file MIME types) and
`ACTION_VIEW`. It passes the URL or the `content://` bytes to Rust. This is glue Kotlin, a few
lines, not duckeye logic. **My call:** write it by hand, not with a community plugin, so it
stays small and auditable.

### The view

The WebView shows the HTML from `duck_blocks_to_html`, with one stylesheet that follows the
system light or dark theme. Links open in the browser.

Relative links and images resolve through `<base href="<page URL>">`, which the WebView
already honours, so the app adds no URL logic. Measured: webbed keeps them relative. The
Wikipedia "Python" markdown has 457 `./Python_(…` links and protocol-relative
`//thumb.wikimedia.org` images. **My call:** remote images load, because this is a reader
view. Actions: share the markdown out (the
wasm spike proved the share sheet), and copy. **My call:** no outline or search in v1.

### Fetch

Rust (`ureq` in the spike) with a desktop-browser user agent and a timeout. No cookies.
A page that needs a login shows the error, not a half page.

### Where the code lives (Teague, 2026-11-10)

A new repo. It pins a duckeye commit, and its build runs that commit's `duckeye --emit-sql`.
**My call:** the name `duckeye-android`. Teague approved; the repo is private. This
design stays in the duckeye repo, because it changes what duckeye must provide
(`--emit-sql`). The plan and the code go in the new repo.

### Distribution (Teague, 2026-11-10)

GitHub releases on the new repo. A signed APK is attached to each release, and Teague installs
or updates from anywhere. Android refuses an update signed by a different key, so one release
key is kept for the app's whole life. **Open:** where that key lives (Teague's machine or a CI
secret), and whether the repo is public. A public repo makes the APK public. F-Droid and the
Play Store are out of scope for v1.

## Phases

Each phase ends with a test on the phone.

1. **One libduckdb.so.** Solo builds of duck_block_utils, webbed and markdown, then one build
   with `STATICALLY_LINK_EXTENSIONS` listing all three. Gate: the spike app, without
   `LOAD`, converts the Wikipedia page with the same bytes as native. A hash is printed on
   the phone. Also measure the cold start honestly, from a fresh process.
2. **Share-in and the view.** The intent filter, `duck_blocks_to_html`, the stylesheet, and
   share and copy out. Gate: share a page from Chrome to duckeye, away from home Wi-Fi.
3. **panduck formats.** Link panduck v0.8.0. Share a docx and an epub from the Files app.
4. **Code view.** Link sitting_duck. Share a `.py` and a `.rs` file.
5. **Shared SQL.** Use `duckeye --emit-sql` when the SQL-core design lands it. CI checks
   that the app's embedded SQL matches the script.
6. **PDF** (later). The pdf extension, with poppler, tesseract, leptonica, libharu and qpdf
   from vcpkg.

## Risks

- **Static linking of out-of-tree extensions: tested for three in phase 1.** panduck and
  sitting_duck are not yet tested. Fallback: loadable files with the store-trust patch
  (spack-packages#7513).
- **Class names shared between extensions.** Measured in phase 1: webbed and markdown both
  define `duckdb::DuckBlockFunctions`. Loadable files never meet, so only a linked build
  fails. The spike renames webbed's class in a scratch clone and builds with
  `DUCKDB_SKIP_APPLYING_PATCHES=1`. The upstream fix is Teague's call. Each new linked
  extension can clash the same way; its solo build does not show it.
- **The APK size.** sitting_duck carries 28 grammars. **Inferred:** about 60-120 MB in the
  APK. Measure it in phase 4.
- **Static linking of the vcpkg libraries** (libxml2, cmark-gfm, pugixml, yaml-cpp) into one
  library can clash on symbols. A loadable `.so` hides its symbols, but a static archive hides
  nothing. One vcpkg baseline removes version clashes. Measured in phase 1: libxml2 (webbed),
  cmark-gfm (markdown) and zlib from vcpkg linked into one library with no clash. Each later
  phase adds libraries (panduck: pugixml, miniz, yyjson), so each linked build re-checks.
- **duckdb-rs pins a DuckDB version** (`1.20000.1` = v2.0.0). A DuckDB update needs a matching
  crate.

## Decided by Teague

- Tauri + native DuckDB, not Capacitor + wasm (2026-11-10).
- Build each extension on its own (2026-11-10).
- Extensions linked statically into one libduckdb.so (2026-11-10). After the correction:
  one build with `STATICALLY_LINK_EXTENSIONS`, with solo builds kept as the check
  (2026-11-10).
- The app lives in a new repo (2026-11-10).
- APKs ship as GitHub releases (2026-11-10).
- v1: HTML, markdown and text, panduck formats, code. PDF in a later phase (2026-11-10).
- Must work away from home, with no homelab server or proxy (earlier).
